# Codex Implementation Specification: Remittance Agent Admin Web

## 1. Instructions to Codex

Build a production-ready ReactJS administration portal for managing a money-remittance agent network by country, region, city, agent, outlet, and cashier.

Implement the application incrementally and keep it runnable after every phase. Do not hard-code countries, cities, currencies, limits, fees, compliance rules, or permissions. These values must come from configuration or APIs.

Before changing an existing repository:

1. Inspect the repository structure and existing conventions.
2. Read `README.md`, `package.json`, environment templates, linting rules, and test configuration.
3. Preserve established patterns unless they conflict with this specification.
4. Do not overwrite unrelated user changes.
5. Run linting, type checking, unit tests, and a production build before completing the work.

If no React project exists, create one using Vite, React, and TypeScript.

---

## 2. Product Goal

Create an internal admin web application that allows authorized employees to:

- Configure countries, regions, and cities.
- Configure supported remittance corridors.
- Onboard and approve agents.
- Manage agent outlets and cashiers.
- Configure transaction limits, fees, exchange-rate margins, and commissions.
- Track agent liquidity and prefunded balances.
- Review transactions, settlements, reconciliations, and compliance alerts.
- Suspend or reactivate agents and outlets.
- Maintain a complete audit trail.
- Restrict functions and data using role-based access control.

This application is an administration portal. It must not directly hold customer funds or independently make final regulatory decisions.

## 12. Remittance Corridors

A corridor controls transfers between an origin country and a destination country.

```ts
interface RemittanceCorridor {
  id: string;
  originCountryId: string;
  destinationCountryId: string;
  sourceCurrencyCode: string;
  destinationCurrencyCode: string;
  allowedPayoutMethods: Array<"CASH_PICKUP" | "BANK_DEPOSIT" | "WALLET_DEPOSIT">;
  minimumAmount: number;
  maximumAmount: number;
  dailyCustomerLimit: number;
  monthlyCustomerLimit: number;
  feePlanId: string;
  exchangeRatePlanId: string;
  complianceRuleSetId: string;
  effectiveFrom: string;
  effectiveTo?: string;
  status: "DRAFT" | "ACTIVE" | "SUSPENDED" | "EXPIRED";
  version: number;
}
```

Requirements:

- Prevent an active corridor from referencing inactive countries.
- Validate that the minimum amount is below the maximum amount.
- Prevent overlapping effective periods for conflicting active configurations.
- Show a calculated preview of fees and destination payout.
- Require a reason when suspending a corridor.
- Record every activation, suspension, and configuration change in the audit log.

## 22. Authentication and Session Security

Prefer OpenID Connect or OAuth 2.0 Authorization Code Flow with PKCE.

Requirements:

- Do not store long-lived access tokens in `localStorage`.
- Prefer secure, HTTP-only, SameSite cookies managed by a backend-for-frontend.
- Enforce MFA through the identity provider for privileged roles.
- Implement inactivity timeout warnings.
- Handle 401 by re-authenticating or redirecting to login.
- Handle 403 with a clear unauthorized page.
- Clear sensitive cached data on logout.
- Do not log tokens, identity documents, bank details, or unmasked customer information.

If a backend-for-frontend is not available, document the selected token-storage design and its security tradeoffs.

## 26. Money and Date Rules

- Represent API monetary values as decimal strings or integer minor units.
- Never use JavaScript floating-point arithmetic for financial calculations.
- Format money with `Intl.NumberFormat`.
- Always display the currency code when currencies could be ambiguous.
- Store timestamps as UTC ISO 8601 values.
- Display timestamps using the selected country, outlet, or user time zone.
- Display effective-date configuration using explicit time-zone rules.
- Use a decimal library for client-side previews and label previews as estimates until confirmed by the backend.

## 31. Security Acceptance Criteria

- Unauthorized users cannot access protected routes.
- Hidden frontend actions are also rejected by the API.
- Users cannot query countries or cities outside their assigned scope.
- Sensitive fields are masked by default.
- Authentication tokens and secrets are never logged.
- Document access requires authorization.
- Mutations include anti-CSRF protection when cookie authentication is used.
- User-entered content is safely rendered.
- No use of `dangerouslySetInnerHTML` without an approved sanitizer.
- Dependency scanning is enabled.
- Audit events exist for configuration, approval, suspension, financial adjustment, and compliance decisions.
- Maker-checker control is enforced for configured high-risk operations.

## 32. UX Acceptance Criteria

- Every list supports loading, empty, error, filtering, and pagination states.
- Forms show field-level validation before submission.
- Server validation is mapped back to fields.
- Destructive or high-impact actions require confirmation.
- Actions requiring a reason cannot proceed with an empty reason.
- Users receive clear success or failure feedback.
- Buttons cannot submit the same mutation twice.
- Unsaved changes produce a navigation warning.
- Status history is visible on agent, transaction, settlement, and compliance records.
- Country and city names are displayed instead of raw IDs.

## 37. Important Domain Constraints

- Regulatory requirements differ by jurisdiction and must remain configurable.
- Country activation must require an authorized compliance decision.
- UI configuration is not proof of regulatory authorization.
- Financial records must use immutable ledger and audit patterns.
- Historical fee, exchange-rate, and commission versions must be preserved.
- Agent, outlet, and corridor suspension must not erase transaction history.
- High-risk changes should use maker-checker approval.
- Final fee, exchange-rate, settlement, limit, and eligibility calculations must be validated by the backend.
- The frontend must never be the only enforcement point for security, permissions, geographic scope, transaction limits, or compliance rules.
